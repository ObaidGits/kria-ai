KEY FOR EXPECTED OUTCOMES
  [OK]        Command executed successfully on remote target
  [APPROVAL]  High-risk action may require explicit approval based on policy profile
  [PIN]       PIN gate expected when policy requires PIN for destructive/sensitive action
  [MULTI]     Multi-step flow (for example install + verify)
  [WARN]      Advisory warning (for example sudo non-interactive hint)
  [BLOCK]     Should be blocked by safety policy
  [FAILFAST]  Clear error with reason; no fake success
  [INTEL]     Intelligence engine routing (ExecutiveController / Planner / SelfModel)
  [AUTO]      Autonomous investigation triggered (CuriosityLoop gathering VM evidence)
  [PREEMPT]   Voice preemption: VM task paused for higher-priority local command
  [PLAN]      StructuredBranchingPlanner evaluating multiple diagnostic paths

REMOTE ROUTING BEST PRACTICES
  1. For guaranteed remote routing, include one of these markers:
     - "on my VM"
     - "via SSH"
     - an explicit ssh pattern: ssh user@host "command"
  2. Most reliable format:
     Please run on my VM via SSH: ssh user@host "your command"
  3. If multiple remote targets are enrolled, include explicit host/user@host.
  4. Remote commands are non-interactive. If sudo asks password interactively,
     KRIA returns a sudo hint and command fails safely.

KNOWN REMOTE CAPABILITIES
  - Executes shell commands on enrolled targets through execute_fleet_command.
  - Auto target selection when target is omitted (best ready target).
  - Target hint supported through host/user@host/display/target id.
  - Remote package install/uninstall intent supported when prompt includes remote context.
  - Fleet events available through /api/fleet/events (SSE) for terminal/status telemetry.

────────────────────────────────────────────────────────────────────────────────
  9A.1 — REMOTE TASK PRIORITY & PREEMPTION
────────────────────────────────────────────────────────────────────────────────

[INTEL-VM-01] Prompt : "Install htop on my VM"
               (while a local background task is running)
              EXPECTED: [INTEL] [OK] Remote install routed as TaskPriority::Interactive (P1).
                        Local background task (P3) yields if needed.
                        Install executes on remote target; result streamed back.
              Notes  : Without ExecutiveController, remote and local tasks compete
                        for the same execution slot. With Executive, priorities are strict.

[INTEL-VM-02] Prompt : "Hey Ria, stop that VM task and check my local CPU now."
               (while a remote package install is running)
              EXPECTED: [PREEMPT] Voice (P0) preempts remote task (P1:Interactive).
                        Remote install paused → local CPU check runs immediately.
                        Response: 🗣️ "CPU at 32%, VM package install paused. Resume?"

────────────────────────────────────────────────────────────────────────────────
  9A.2 — MULTI-PATH PLANNING FOR REMOTE DIAGNOSTICS
────────────────────────────────────────────────────────────────────────────────

[INTEL-VM-03] Prompt : "My VM is running slow. Figure out what's wrong."
              EXPECTED: [PLAN] StructuredBranchingPlanner generates 3 diagnostic paths:
                        Path A (DiagnoseFirst): ssh → top → free → df → iostat → analyze
                        Path B (MinimalRisk): ssh → uptime → free (read-only, minimal)
                        Path C (Aggressive): ssh → systemctl restart docker (assumes docker)
                        SelfModel scores each path. Winner: Path A (highest geomean).
                        Evidence gathered → FailureAnalyzer categorizes:
                          "OOM killer active — container using 3.8 GB / 4 GB limit."
              Notes  : WorkingSet summarizes all remote command outputs into LLM context.
                        SelfModel tracks per-tool success rates across sessions.

[INTEL-VM-04] Prompt : "My VM seems broken. Fix it."
              EXPECTED: [INTEL] UncertaintyRouter classifies as LOW confidence.
                        Ambiguous: "broken" could mean network, disk, services, etc.
                        Route: Ask for clarification first.
                        "What specifically isn't working? Network, services, disk space,
                        or something else?"
              Notes  : Without UncertaintyRouter, system would guess or try everything.
                        Thresholds: plan≥0.7, gather≥0.4, ask≥0.3.

  9A.4 — SKILL COMPILATION FROM REPEATED REMOTE PATTERNS
────────────────────────────────────────────────────────────────────────────────

[INTEL-VM-07] Prompt : "Check disk space on my VM"
               (asked 3 times with different approaches across sessions)
              EXPECTED: [INTEL] SkillCompiler recognizes repeated pattern after 3 successes:
                        ssh {host} df -h
                        CompiledSkill with typed variable: host: VariableType::IpAddress
                        QuarantineRegistry holds for HITL approval.
                        "I've compiled a shortcut skill 'check_vm_disk'."
                        "It's in quarantine. Approve to use for faster future checks."
              Notes  : N=3 gating requires 3 successes with varied variable values.
                        VariableSafety validates against shell injection.

[INTEL-VM-08] Prompt : "Check if docker is running on all my VMs"
              EXPECTED: [PLAN] Planner creates multi-target plan:
                        For each enrolled VM target:
                          ssh {host} "systemctl is-active docker"
                        Results aggregated. SelfModel tracks success per target.
                        If a target consistently fails, SelfModel lowers its path score.
                        Response: "Docker is active on 2/3 VMs."
                                  "192.168.122.240: active"
                                  "192.168.122.241: inactive (last check failed too)"
                                  "192.168.122.242: active"

────────────────────────────────────────────────────────────────────────────────
  9A.5 — WORLD MODEL & FAILURE HISTORY FOR REMOTE TARGETS
────────────────────────────────────────────────────────────────────────────────

[INTEL-VM-09] Prompt : "Why did the VM install fail last time?"
              EXPECTED: [INTEL] WorldModel stores remote command outcomes.
                        FailureAnalyzer matches stderr to known patterns:
                          - "Unable to locate package" → package name typo or missing repo
                          - "Could not get lock" → another apt process running
                          - "Permission denied" → sudo not configured
                        Response grounded in actual historical failure:
                          "Last install failed: 'Could not get lock /var/lib/dpkg/lock-frontend'."
                          "Another package manager was running. Try again?"
              Notes  : WorldModel persists across sessions (SQLite).
                        Failure patterns: OOM, permission, config, dependency,
                        network timeout, port conflict, resource exhaustion.
