# Implementation Plan — OpenClaw Intelligence Enhancements

## Overview
Builds KRIA's capability-*engineering* layer so it reasons like a senior engineer (classify goal →
infer hidden requirements/constraints/unknowns → generate strategies → iterate → compare on
confidence+cost → compose → execute → reflect → learn) while OpenClaw and other providers stay pure
hands. Composition feeds the **existing** HTN runtime (no new executor). The abstraction is
**Capability** (not "Skill"). Every phase is flag-gated; flag-off ⇒ byte-identical legacy. No hardcoded
prompts/keywords/provider branches. Read `requirements.md` and `design.md` (esp. §5 Architecture, §9
Arbitration, §10 Intelligence, §27–§32) before starting.

### Execution protocol (applies to EVERY task)
1. Top-to-bottom; respect the wave graph. Don't start a task with incomplete predecessors.
2. Read cited design sections before coding.
3. **DONE only when ALL hold:** `cargo check`/`clippy`/`fmt` clean (UI: `npm run build`); the task's
   unit/integration tests written + green; **flag-off parity** proven by a test; **wiring asserted**
   (R25) where the task adds a call path; real code, no fabricated results; no hardcoded prompt/
   keyword/provider-name branch (CI gate green).
4. **Wiring row rule (R25/§34):** a task that adds a backend component is NOT done until its full
   wiring-map row exists — the `cpp_*` command(s) registered, the `capability:*` event(s) produced,
   the frontend view/store consuming them, and the existing-KRIA touchpoint connected. No backend-only
   component; no dangling command/event/view.
5. Check the box; STOP for review at each milestone boundary.
6. Blocked/ambiguous ⇒ leave unchecked + report; don't guess.
