# Implementation Plan: GUI Cognition LIVE Remediation

## Overview

Seven sequential, **live-gated** phases fixing the live GUI Cognition path on Wayland/GNOME, driven
by the live True-Test (`planning_docs/gui_cognition_user_truetest_results.md`). A phase is "done"
only when: (a) code implemented behind its flag (flag-OFF = byte-for-byte unchanged), (b) CI-safe T2
tests green, (c) the phase's **live prompt subset** re-run hits its gate (executed+verified, or
correct ask/gate), (d) 0 destructive-leak, (e) no regression in prior phases. **Do NOT start a phase
until the previous phase's live gate is green.** Verification is never weakened to pass.

Baseline live: **PASS 10 · PARTIAL 36 · FAIL 66 · 0 leak** (112 prompts).

## CRITICAL FINDING (live debug during Phase 1) — read before executing

A live capture of "Open the calculator" revealed the **dominant upstream root cause**, deeper than
Issues #1–#7: the GUI-cognition LLM planner routes to the active chat provider
(`active_provider = "opencode"`, `cloud_model_id = "deepseek-v4-flash-free"`) which is
**NOT grammar-capable** — it returns prose, is rejected every turn
(`planner.mode = "llm_rejected_fallback"`, `llm_status = "rejected_after_repair"`,
`capability.status = "not_grammar_capable"`), so the **deterministic fallback** drives every turn.
That fallback cannot extract the target app: "Open the calculator" yields `intent = analyze_plan`,
`target_app_kind = unknown`, and `target_app_hint = Devin` (the CURRENT active window), so OpenApp
runs against the wrong target and the calculator never actually opens (`pgrep` confirms). This
explains the generic plans, wrong targets, NO_PROGRESS/BLOCKED_PLAN_CLARIFY, and the
verification_failed downgrades across the whole live run.

The code already detects/handles grammar-capability correctly (Task 2 work). The defect is that the
**cloud path is unconstrained**: `LlmBackend::chat_with_grammar` falls back to plain `chat` for
cloud (OpenAI-compatible) backends, and `supports_grammar` is a binary that is `false` for cloud, so
the planner sends free text → prose → reject → deterministic fallback → wrong target. The fix is a
**shared multi-backend structured-output adapter** (Task 0) so BOTH local and cloud return
schema-valid typed plans — giving users a real local-OR-cloud choice. **Phase 1's verifier fix is
correct and landed, but its live gate cannot pass until the planner emits correct targets.**
Therefore **Task 0 (below) is the true first blocker** and must be green before Task 1's live gate.
