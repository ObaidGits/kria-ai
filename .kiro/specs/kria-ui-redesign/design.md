# KRIA UI Redesign — Design

## Overview

This document is the implementation blueprint for the KRIA desktop UI. It pairs the product/UX design (from `KRIA_UI_REDESIGN_MASTERPLAN.md`) with a **researched, justified technology and architecture specification**. It is written so designers can build every screen and engineers can implement without inventing architecture.

**Guiding constraints (drive every decision):** local-first; UI must stay smooth while local AI saturates CPU/GPU; low CPU/GPU/RAM/battery; Linux-primary (GNOME/KDE, Wayland/X11); calm/premium/AI-first; keyboard-first; WCAG 2.2 AA; hybrid 2D-default + 3 selective 3D lenses.

**Cross-validation of source docs:** The inventory (current state) and masterplan (target) were cross-checked. Confirmed facts used here: current stack is **Tauri v2 + SolidJS + Vite** with hand-written CSS, ~230 Tauri commands, ~30 event channels, chart.js present-but-unused-in-views, 73% hardcoded colors, dual/dangling design tokens, 8 orphaned components, inert workflow stubs. These are treated as the migration baseline.

## 1. Technology Stack — Research & Decisions

Each decision lists the choice, the alternatives considered, and the evidence-based rationale against KRIA's constraints. Where a decision reaffirms the existing stack, that is deliberate and evidence-based (avoid rewrite-for-rewrite; the Rust backend + ~230 commands already exist).

### 1.1 Desktop shell — **Tauri v2** (keep & double down)
- **Alternatives:** Electron, Wails (Go), native GTK/Qt, Neutralino.
- **Evidence:** Tauri v2 (stable since late 2024) uses the system webview + a Rust core, yielding ~90% lower memory and dramatically smaller binaries than Electron (which bundles Chromium+Node); idle RAM ~20–40 MB class vs Electron's hundreds. KRIA already has a large Rust/`kria-core` backend and ~230 Tauri commands.
- **Rationale:** For a *local-first AI OS* where the models must own the CPU/GPU/RAM, bundling a second Chromium (Electron) is disqualifying. Tauri's system-webview model is the lowest-footprint mature option and is already integrated. Electron rejected (RAM/battery). Wails rejected (would abandon the existing Rust core). Native GTK/Qt rejected (loses web-tech velocity, huge rewrite, weaker cross-platform for this team).
- **Linux note:** Tauri uses WebKitGTK on Linux — the design must validate against WebKitGTK's capabilities (see §7 risks: WebGL/graph performance, backdrop-filter blur cost). This is the single biggest platform risk and is mitigated in §5/§7.

### 1.2 UI framework — **SolidJS** (keep & double down)
- **Alternatives:** React (19/compiler), Svelte 5, Vue, Qwik, Vanilla.
- **Evidence:** Solid's fine-grained reactivity updates only the exact DOM nodes that change (no virtual DOM, no reconciler); benchmarks put it ~5% over vanilla vs React ~100% slower; ~7 KB core vs React ~40 KB. KRIA already uses Solid.
- **Rationale:** The hard requirement "UI stays smooth while agents stream tokens/tools/telemetry" is exactly where fine-grained reactivity wins — streaming updates touch only affected nodes, avoiding full-tree re-renders under load. React rejected (re-render overhead under high-frequency AI event streams; heavier). Svelte 5 is comparable but switching abandons the existing Solid codebase for no net gain. Solid confirmed.
- **Fix carried in:** the current single `appStore` god-object is an anti-pattern → modularize (see §3).

### 1.3 Build/dev — **Vite** (keep)
- **Rationale:** Already used; best-in-class HMR + Solid plugin; fast DX; tree-shaking for the lazy-loaded Spaces/lenses. No change.

### 1.4 Styling & design tokens — **Tokenized CSS (custom properties) generated by Style Dictionary; no runtime CSS-in-JS**
- **Alternatives:** Tailwind, vanilla-extract, CSS-in-JS (styled/emotion), plain hand CSS (current), UnoCSS.
- **Rationale:** The #1 current defect is token drift (73% hardcoded, dual `:root`, 7 dangling vars). The cure is a **single token source** compiled to CSS custom properties (dark+light) via **Style Dictionary**, consumed by a small set of hand-authored component styles. Runtime CSS-in-JS rejected (per-render cost — violates the performance budget). Tailwind considered (utility consistency) but rejected as primary because (a) it encourages inline value drift unless strictly governed, (b) design here is token/semantic-driven, (c) adds build/markup weight; a thin utility layer MAY be added for spacing only. Plain hand-CSS (current) rejected as the primary discipline because it produced the drift. **Decision:** Style Dictionary → CSS variables → component CSS modules; lint rule forbidding raw hex/color in components (enforces Req 14.2).

### 1.5 Accessible component primitives — **Kobalte** (Solid) as the a11y foundation
- **Alternatives:** build all primitives in-house, Ark UI, Melt.
- **Rationale:** Kobalte is the mature, WAI-ARIA-compliant headless primitive library for Solid (dialog, menu, popover, listbox, tabs, tooltip, etc.). Building focus-trap/ARIA/keyboard from scratch for every primitive is error-prone and is the exact gap the current app has (no focus rings, div-buttons). Kobalte gives correct semantics/keyboard/focus for free; KRIA's visual layer styles it via tokens. This directly satisfies Req 17. In-house-only rejected (a11y risk); Ark/Melt are Solid-capable alternatives but Kobalte is the most established for Solid.

### 1.6 Motion — **CSS-first (transitions/keyframes) + Web Animations API for orchestration; no heavy JS animation lib**
- **Alternatives:** GSAP, Motion One, Framer-Motion-equivalent, anime.js.
- **Rationale:** Compositor-driven CSS transforms/opacity are the cheapest smooth motion (GPU-composited, off main thread) — mandatory for the low-power budget. A tiny WAAPI helper handles sequencing (Space/mode transitions, Core state changes). Heavy libs (GSAP) rejected for general UI (bundle + main-thread cost) though a scoped use MAY be justified for the Core if a spike shows CSS insufficient. Motion tokens (durations/easings) live in the token system. Satisfies Req 16.4.

### 1.7 The Core rendering — **Layered CSS/SVG with a lightweight shader only if a spike requires it**
- **Alternatives:** full WebGL/Three scene, Lottie, canvas 2D, CSS/SVG.
- **Rationale:** The Core is the only always-present animated element → it must be the cheapest possible. Default: CSS/SVG gradients + transforms + subtle filter, driven by state tokens. A single small WebGL/shader layer is permitted ONLY if design/motion studies prove CSS/SVG can't achieve the "living aura" within budget, and even then it must idle at a low frame cap and freeze under reduced-motion. Lottie rejected (JSON animation runtime cost + less state-driven control). Decision: CSS/SVG-first; shader as a contained, budgeted fallback.

### 1.8 3D lenses (Memory Graph, Constellation) — **Three.js constrained by a strict budget; OGL as fallback if the spike fails**
- **Alternatives:** Three.js, OGL, regl, Babylon.js, PixiJS (2.5D), 2D-canvas-only.
- **Rationale:** Only 2 true 3D lenses + 1 shallow 2.5D (plan-compare). Babylon rejected (heavy, game-engine scale). PixiJS is excellent for 2.5D and is a strong option for the Constellation and even the graph rendered as 2.5D — kept as an alternative. **Primary decision: Three.js** for the graph/constellation because it is the most mature, has instanced rendering (`InstancedMesh` for thousands of nodes cheaply), points/line materials, and broad WebGL support — but governed by hard rules (§5.4): node caps, LOD, instancing, frustum culling, on-demand mount, freeze-to-static when idle, unload on exit, auto-degrade to the 2D fallback under model load / reduced-motion / WebKitGTK weakness. **Fallback:** if a WebKitGTK/Linux performance spike shows Three.js too heavy, drop to **OGL** (minimal WebGL, tiny footprint) or the mandatory 2D-canvas fallback. A `WebGL-not-available` path is required regardless (Req 5.5/17.5). Decision is a spike-gated primary (Three.js) with a defined fallback ladder — no ambiguity about the path.

### 1.9 Graph layout computation — **ngraph.forcelayout in a Web Worker (off main thread), freeze on settle**
- **Alternatives:** d3-force (main thread), ngraph (worker), server-side layout.
- **Rationale:** Layout physics must never block the UI thread (Req 16). ngraph.forcelayout is fast and worker-friendly; run it in a worker, stream positions until alpha settles, then **stop** (no perpetual simulation). d3-force is fine for small 2D fallbacks but ngraph scales better and off-thread satisfies the budget. Server-side rejected (adds backend coupling for a view concern).

### 1.10 List/virtualization — **@tanstack/virtual (Solid adapter)**
- **Rationale:** Chat, memory lists, logs, timelines can be long; virtualization is required (Req 16.2). TanStack Virtual is framework-agnostic with a Solid adapter, headless, tiny, and battle-tested. Building custom virtualization rejected (reinvention risk). Confirmed.

### 1.11 Charts — **uPlot for time-series; token-styled SVG/CSS for simple stats**
- **Alternatives:** Chart.js (currently a dependency, unused in views), ECharts, D3, uPlot, Recharts.
- **Rationale:** Observatory/Analytics need fast, low-cost charts. uPlot is the smallest/fastest canvas time-series library (built for thousands of points at low CPU) — ideal for live resource/telemetry. Chart.js rejected as primary (heavier, and it's already dead weight in the current app) though acceptable for occasional non-live charts. ECharts/D3 rejected as default (bundle/complexity). Simple KPI bars remain token-styled SVG. Confirmed uPlot + SVG.

### 1.12 Command Palette — **in-house Solid component on Kobalte primitives**
- **Rationale:** kbar/cmdk are React. Build a small Solid palette using Kobalte listbox/dialog for a11y + a fuzzy matcher (e.g., a tiny fuzzy lib). This is core to nav (Req 2) and must be perfectly keyboard-accessible and fast. In-house is justified (no mature Solid equivalent; it's small).

### 1.13 Docking / resizable panels / detach — **in-house split/resize primitives + Tauri multi-window for detach**
- **Alternatives:** golden-layout/dockview (React/framework-coupled), rc-dock, build custom.
- **Rationale:** No mature Solid docking library. KRIA's needs are constrained (lanes/rails + a capped detach set, not arbitrary docking), so a lightweight custom split-pane + resizer + collapse system is simpler, lighter, and fully controllable — and multi-monitor detach is a **Tauri window**, not an in-DOM docking framework. Heavy docking libs rejected (framework mismatch + weight + they encourage the panel-sprawl anti-pattern §45). Confirmed custom + Tauri windows.

### 1.14 Window management — **Tauri window APIs; KRIA-owned in-app mode switch**
- **Rationale:** Modes (Compact/Standard/Immersive), geometry memory, multi-window detach, tray, fullscreen use Tauri's window/tray APIs. KRIA provides its own mode switch (Req 15.5/18.3) rather than relying on OS-specific window controls. Linux fallbacks per Req 18.

### 1.15 Icons — **Lucide, delivered as an SVG sprite**
- **Alternatives:** Lucide, Phosphor, Tabler, Heroicons, custom.
- **Rationale:** Need one coherent line-icon set with a single stroke weight (replaces emoji-as-icon). Lucide is open, consistent, comprehensive, tree-shakeable, and sprite-able for zero per-icon runtime cost. Phosphor/Tabler are fine alternatives; Lucide chosen for stroke consistency + license + ecosystem. Emoji reserved for user content only (Req 14.6).

### 1.16 Typography — **self-hosted bundled woff2** (display + text + mono)
- **Rationale:** Fonts must be bundled (current app declares Space Grotesk/IBM Plex/JetBrains but may not bundle → inconsistent across Linux). Self-host woff2, subset for latin + needed scripts, to guarantee identical rendering across GNOME/KDE (Req 18.4). Exact families chosen at visual-design stage; roles fixed: one display, one text (high legibility), one mono.

### 1.17 Markdown & code — **keep marked + DOMPurify; highlight.js now, evaluate Shiki lazily**
- **Rationale:** Chat renders markdown; keep the proven marked + strict DOMPurify sanitization (security-critical). highlight.js is lighter for live streaming; Shiki gives better fidelity but is heavier — allowed only lazy-loaded for non-streaming code blocks if desired. No change to the security posture (sanitize all AI/tool HTML).

### 1.18 State & events — **Solid stores/signals (modularized) + a small typed event bus** (see §3)
### 1.19 Testing — **Vitest (unit) + @solidjs/testing-library (component) + Playwright (E2E)** (keep, expand)
### 1.20 Component docs / design-system workbench — **Histoire** (Vite-native Storybook alternative)
- **Rationale:** Histoire is Vite-native and Solid-compatible, lighter than Storybook, and shares the Vite config → faster, less overhead. Storybook acceptable but heavier. The component kit (Req 14.4) is documented here so contributors extend without breaking consistency.
### 1.21 Packaging — **Tauri bundler**, Linux-first artifacts (AppImage + .deb), then Windows/macOS.
### 1.22 Performance profiling — **Web devtools + custom performance marks** around Space switch, first-token, lens mount, list scroll; a lightweight in-app perf HUD (dev-gated in Observatory Diagnostics).

## Architecture
_(Application architecture — layered model, routing, state/event, lazy-loading.)_

### 2.1 Layered model
```
┌─ Shell layer ──────────────────────────────────────────────┐
│ AppShell: PresenceBar(Core, Intent/Palette, Approvals, Settings) │
│           Dock · SpaceRouter · InspectorHost · StatusLine        │
├─ Space layer (lazy) ───────────────────────────────────────┤
│ Converse · Memory · Automations · Capabilities · Machines ·      │
│ Observatory · Settings   (each = a route + a store slice)        │
├─ Overlay layer (global, singletons) ───────────────────────┤
│ CommandPalette · ApprovalCenter · NotificationCenter · Inspector │
│ CoreController · VoiceSurface · Confirm/Modal host · Toasts      │
├─ Component kit (design system) ────────────────────────────┤
│ primitives (Kobalte-backed) + KRIA-styled kit + tokens           │
├─ Data/runtime layer ───────────────────────────────────────┤
│ stores (per Space) · event bus · Tauri bridge (commands/events)  │
│ workers (graph layout) · lenses (Three.js, on-demand)            │
└────────────────────────────────────────────────────────────┘
```

### 2.2 Routing & window
- Internal router maps `space[/segment][/entityId]` so every context is addressable/deep-linkable and restorable (Req 1.4/1.5). Not the current hash-nav; a small typed router with state restoration.
- Window modes (Compact/Standard/Immersive) are a top-level UI state that reconfigures the shell composition (which regions render/collapse) per §25/§52 of the masterplan. Mode is orthogonal to the active Space (Req 15).

### 2.3 Lazy loading / code-splitting
- Each Space is a lazily-loaded chunk (only Converse + shell in the initial bundle → fast startup, Req 16). The 3D lens engine (Three.js) and graph worker load only when a lens opens. Charts (uPlot) load with Observatory. Markdown/highlight load with Converse.

## 3. State & Event Architecture (fixing the god-store)

### 3.1 Modular stores (replace single `appStore`)
- **shellStore**: active Space, window mode, palette open, inspector target, theme, density.
- **coreStore**: Core state machine (the 14+ states, Req 3) — a single source that every surface reads; fed by domain events.
- **converseStore**: threads, active thread, messages, work-lane blocks, context rail, composer draft.
- **memoryStore**, **automationStore**, **capabilityStore**, **machineStore**, **observatoryStore**, **settingsStore**: per-Space.
- **approvalStore**: unified queue for all HITL/decision/gui/workflow approvals (Req 11).
- **notificationStore**: batched notices (Req 13).
- **voiceStore**: voice mode + live state (drives coreStore).
Each store owns its slice, exposes signals + actions; no cross-store reach-in except via the event bus.

### 3.2 Typed event bus (replace scattered `listen` in one god file)
- One typed bridge subscribes to Tauri events and dispatches into a typed internal bus; stores subscribe to the events they care about. Benefits: testable, no single 1000-line listener, clear ownership.
- **Streaming discipline:** high-frequency streams (tokens, tool events, telemetry) update only their target signal (Solid fine-grained) — no store-wide notifications. Batch bursts with a microtask/rAF coalescer for telemetry (the current app already does an rAF batch for intelligence events — generalize it).

### 3.3 Backend contract (consumed, not redesigned)
- The UI consumes existing Tauri commands (~230) and events (~30). The disposition map (Req 20.1) assigns each to a Space. **Contract changes explicitly required by this redesign** (to be coordinated with backend): (a) unify HITL/decision/gui/workflow-resume events into an approval-event shape the Approval Center consumes, and (b) register the currently-unregistered `workflow_*` commands so workflow HITL/cancel/continuation stop being inert (Req 11.6). All other contracts remain; UI degrades gracefully when optional services are absent (Req 20.4).

## 4. Design System

### 4.1 Token architecture (single source → CSS variables)
Token groups (one source of truth, dark+light): **color** (neutral scale ×~6, accent teal + hover, semantic success/warning/danger/info soft/solid/text, risk ramp green→yellow→red→black, surface tiers ×4), **elevation** (×4 + shadow), **space** (4-based scale), **radius** (scale), **type** (families display/text/mono, size roles display/title/heading/body/caption/micro, weight, line-height, measure), **motion** (durations 120/200/400, easings), **z-index** (named layers: canvas/panel/floating/modal/approval), **blur** (floating-only). Lint forbids raw color in components (Req 14.2).

### 4.2 Component kit (one per concept — Req 14.4)
Button, IconButton, Input, Select, Textarea, Search, Card, Chip, Badge, StatusDot, Row/ListItem, SegmentBar, Table, Tabs, Tooltip, Popover, Menu, Dialog/Confirm, Wizard, EmptyState, Progress/Meter, Inspector, ApprovalCard, WorkBlock, GraphNode/Edge (shared 2D/3D grammar), Notification, CorePresence, Composer, ThreadRow, MemoryCard, CapabilityRow, DeviceRow, WorkflowCard, RunTimeline, EvidenceViewer. Each: variants + all interaction states (§ Interaction Bible in masterplan §29) + tokens + Kobalte base where interactive + Histoire story. No surface may re-implement a concept (Req 21.2).

### 4.3 Visual language ("Ink & Aura", masterplan §22)
Deep still ink canvas + soft radial depth; 3 material tiers (content opaque / floating aura-glass with blur / the luminous Core); 4-step elevation by light; neutral-dominant, accent-scarce color; type-led hierarchy. Blur only on floating layers (perf + WebKitGTK cost). Dark default; full light parity; optional follow-OS.

## 5. Rendering & Performance Strategy

### 5.1 Reactivity discipline
- Fine-grained signals; components never re-run wholesale. Derive with memos; keep list items keyed and virtualized. Avoid large reactive objects where a store with granular paths suffices.

### 5.2 Virtualization & lazy content
- Virtualize chat, memory lists, logs, run timelines, fleet tables (@tanstack/virtual). Off-screen Spaces unmounted. Heavy media (images) lazy + capped.

### 5.3 Motion budget
- CSS transform/opacity only for UI motion; ≤200 ms (≤400 ms for Space/mode change); event-driven; Core is the only ambient animator; global reduced-motion kill-switch covers CSS AND the Core AND freezes 3D (fixes the current gap where JS loops escaped reduced-motion).

### 5.4 3D lens governance (hard rules — Req 16.3)
- **Mount on demand**, unload on Space exit. **Node/element caps** ("top N by relevance") with a visible "showing N of M." **Instanced rendering** for nodes/edges. **LOD**: distant nodes simplify; labels only for focused/near set. **Frustum culling.** **Layout in a Worker**, stop when settled → then the scene is **static** (no perpetual render loop). **Freeze to a still frame** when idle/unfocused; resume render only during interaction. **Auto-degrade to 2D** under heavy model load, reduced-motion, or WebGL unavailability. **Camera:** damped, constrained orbit; reset-view always available. **Lighting/material:** single soft key + ambient, matte, accent = selection only. Every lens has a **2D/keyboard fallback** (Req 5.5/7.5/17.5).

### 5.5 Startup
- Initial bundle = shell + Core + Converse only. Everything else lazy. Target instant first paint of the calm home; provisioning wizard gates only first-run.

### 5.6 Performance acceptance targets (measured via §1.22 marks)
- Space switch < 150 ms; palette open < 100 ms; first streamed token render < 50 ms after event; list scroll 60 fps virtualized; idle main-thread ~0 (Core only); lens interaction ≥ 30 fps on target Linux hardware or auto-degrade. These are gates in the Definition of Done.

## 7. Risk Analysis & Tradeoffs

| Risk | Impact | Mitigation |
|---|---|---|
| **WebKitGTK (Linux) WebGL/blur performance** weaker than Chromium | 3D lenses / aura-glass may stutter on Linux | Spike early (§1.8); budget rules (§5.4); blur only on floating layers; auto-degrade to 2D; OGL/2D fallback ladder; test on GNOME+KDE Wayland+X11 before committing Three.js |
| **3D scope creep** | perf + complexity | Only 2 lenses + 1 2.5D; hard caps; on-demand/freeze/unload; 2D fallback mandatory |
| **God-store refactor churn** | migration cost | Modular stores + event bus introduced incrementally per Space; parity tests |
| **Backend contract change** (approval unification, workflow command registration) | cross-team | Small, explicit, coordinated (§3.3); everything else unchanged |
| **Token migration** (73% hardcoded today) | large edit surface | Style Dictionary + lint gate; migrate Space-by-Space |
| **Motion under reduced-motion / JS loops** | a11y + battery | global kill-switch covers CSS + Core + freezes 3D |
| **Fractional scaling / mixed-DPI (Linux)** | layout crispness | relative scale (no px breakpoints), mode-based composition, test mixed-DPI |
| **Global hotkey / tray / always-on-top unavailable (Wayland)** | summon/presence | enhancement-with-fallback (Req 2.5/18.2) |
| **Detachable-window sprawl** | complexity | capped detach set; primary window remains OS |

### 7.1 Key tradeoffs accepted
- **Keep Tauri+Solid** over a trendier rewrite → less novelty, far better fit + lower risk (evidence-based).
- **Three.js primary** (mature) over minimalist OGL → slightly larger bundle, but instancing/ecosystem + spike-gated fallback de-risks it.
- **CSS tokens over Tailwind** → less utility velocity, but eliminates the drift that caused the current mess (the actual problem to solve).
- **In-house palette/docking** → build cost, but correct fit + no framework mismatch + avoids panel-sprawl.

## Testing Strategy
- **Unit** (Vitest): stores, event bus, reducers, token/lint rules, fuzzy matcher, layout math, mode/degradation logic.
- **Component** (@solidjs/testing-library): kit components across all interaction states; a11y assertions (roles/labels/focus); Approval card; WorkBlock; Composer.
- **E2E** (Playwright): the flow maps (masterplan §33) — launch→work, voice→approval→execute→memory, automation authoring, memory correction, capability install, failure recovery; window-mode transitions preserve state; multi-window approval mirroring.

## Error Handling

- **Command failures**: surface inline in the relevant surface with plain-language message + a recovery action (retry/alternative/explain); never a silent failure (fixes current silent memory-explain) and never a bare stack.
- **Streaming stalls**: the Core watchdog clears a stalled turn; the Work lane shows a clear "stopped/stalled" state with resume/retry (no infinite spinner).
- **Optional service unavailable** (sidecar/MCP/n8n/ComfyUI/fleet controller): the dependent surface shows an honest degraded state and remains usable for what still works (Req 20.4).
- **Offline / backend not ready**: composer still accepts input (queued); Core shows a "limited" state; no hard blank.
- **3D/WebGL unavailable or under load**: auto-fallback to 2D with a one-line notice.
- **Approval/kill safety**: approvals and global Stop are always reachable, including in Immersive and on the active window in multi-monitor setups (Req 11.4, 15.4).
- **Boot crash**: a recoverable boot-error surface (retry/reload) replaces any white screen.

## 11.2 Technology Re-Validation — the WebKitGTK Correction (P0)

**[CORRECTION to §1.8 / §5.4 / §7]** Deep research (Tauri's official Linux-graphics docs; Mozilla "WebGL composites slowly on Linux"; Tauri issues #5761 "HTML Canvas ~5 FPS on Linux", #9394 NVIDIA/Wayland) establishes that KRIA's **primary** platform renders through **WebKitGTK**, where:
- WebGL has **no fast compositing path** on Linux and can be slow/unreliable;
- even 2D `<canvas>` animation can collapse to single-digit FPS on some setups;
- Wayland + NVIDIA frequently needs `WEBKIT_DISABLE_COMPOSITING_MODE=1` to avoid blank/crash — which *itself* disables accelerated compositing (further hurting GPU paths);
- large/complex DOM degrades faster than on Chromium.

**Corrected decisions:**
1. **The 2D representation of the Memory Graph and Capability Constellation is the DEFAULT on Linux**, not merely a fallback. The 3D lens becomes an **opt-in enhancement**, enabled only after (a) runtime capability detection AND (b) a passing on-device performance probe (§11.3 G2). KRIA must **never auto-launch a 3D scene that will stutter** on the user's driver/DE combo. This *reduces* 3D ambition — consistent with "don't force 3D."
2. **DOM virtualization is mandatory, not optional** (WebKitGTK large-DOM penalty) — every long list/stream is virtualized from day one.
3. **Blur is minimized and spike-tested** (aura-glass compositing cost on WebKitGTK); if blur is expensive on target hardware, fall back to solid translucent surfaces (visual language must survive without blur).
4. **Ship the Linux graphics guidance** (env-flag handling for NVIDIA/Wayland) as a first-class concern, not an afterthought.
5. **Rendering ladder for graphs:** instanced 3D (Three.js) *only where G2 passes* → else 2D SVG for small graphs / virtualized 2D canvas for larger → else virtualized DOM list (always available, always accessible).
6. **Kobalte** confirmed mature for Solid a11y; **Ark UI (Solid, on Zag.js)** recorded as the vetted drop-in alternative if a required primitive is missing from Kobalte. No change to the primary choice.

Net effect: KRIA is designed to be **excellent in 2D on WebKitGTK first**, with 3D as a progressive enhancement for capable machines — the honest, evidence-based posture for a Linux-primary local-first app.

## 11.8 Visual Hierarchy Rules (global, engineer-applicable)

A **5-level weight system** governs every surface. Weight is expressed through (in priority order) **space → type → contrast → elevation → accent → motion**. A component may never exceed its level.

| Level | Role | Visual treatment | Motion allowed |
|---|---|---|---|
| **L1 Primary** | the one focal thing + the one primary action | largest type/most space; highest contrast; may hold the single accent; elevated | state-change only |
| **L2 Secondary** | direct supports of the task | medium contrast; quieter surface; no accent unless it is the surface's single primary | subtle running-pulse (max 1) |
| **L3 Supporting** | metadata, chips, timestamps, counts | low contrast; small type; neutral | none |
| **L4 Background** | canvas, rails-at-rest, dividers-by-space | lowest contrast; ambient depth | none (Core excepted) |
| **L5 Hidden** | progressive-disclosure detail, dev panels | zero weight until opened | reveal ≤200ms |

**Attention-order contract (per Space — first/second/third):**
- **Converse:** 1) forming answer / Core state → 2) composer (agency) → 3) work lane (only if active). Rails are L3/L4.
- **Memory:** 1) selected card or graph → 2) search/segments → 3) relationships/metadata.
- **Automations:** 1) “what can run” / active run → 2) run controls → 3) history/metadata.
- **Capabilities:** 1) the ability in question → 2) grant/run action → 3) governance/metadata.
- **Machines:** 1) fleet health / remote canvas → 2) actions → 3) alerts/telemetry.
- **Observatory:** 1) system pulse → 2) the drilled metric → 3) history.
- **Settings:** 1) search / chosen group → 2) the setting control → 3) risk/history metadata.

**Rules:** exactly one L1 focal + one accent-primary per view; risk color is never used for hierarchy (reserved); type/space do the hierarchy work before color does; adding a new element requires assigning it a level (no unranked elements).

## 11.9 AI Personality Beyond the Core (whole-interface, subtle)

The Core carries most presence, but the **whole interface** subtly reflects KRIA's state — cheaply, never theatrically. Personality = *emotionally intelligent, composed colleague*; never cute, never anthropomorphic, never loud.

| KRIA state | Core | Interface-level cue (subtle, cheap) |
|---|---|---|
| Idle | slow breath | room at rest; nothing animates |
| Listening | inward pull + level | composer/voice line gains focus glow; rest dims slightly |
| Thinking | converging | work lane fades in as a quiet L2 surface; answer area holds a gentle placeholder cadence |
| Planning | branching | plan-compare block appears in work lane; steps enumerate calmly |
| Executing | directed beam | active work block pulses (max 1); target named in plain language |
| Waiting (on user) | held/steady | the relevant control gains a soft attention ring; nothing else moves |
| Learning | warm bloom | brief warm accent flick toward Memory affordance; "Learned: …" in notifications |
| Reflecting/Dreaming (bg) | very dim drift | an unobtrusive Observatory badge; zero foreground change |
| Celebrating (milestone) | one warm bloom | a single tasteful notification; no confetti |
| Curious/uncertain | cooler, calmer | KRIA phrases uncertainty; UI stays calm (never louder when unsure) |
| Confident | steady, clear | crisp, quick reveals; minimal hedging |
| Hesitant | slightly slower | KRIA asks a clarifying question inline; no forced action |
| Blocked / needs-permission | still + risk halo | room desaturates slightly; Approval Center surfaces; the Core "glances" toward it |
| Autonomous (acting for you) | focused | a persistent, quiet "acting" indicator + one-action stop always visible |
| Protective (risk) | still, risk-tinted | risk ramp on the approval; deliberate confirm; nothing else competes |
| Focused (deep work / Immersive) | quiet | chrome recedes; canvas leads |
| Sleeping (quiet hours) | dimmed breath | room dims; motion minimized; notifications batched |
| Recovering (after failure) | unsettled → calm | plain-language recovery inline; no alarm styling beyond risk semantics |

**Law:** interface-level cues must be *cheap* (opacity/dim/one pulse), reduced-motion-safe, and subordinate to content. Under reduced-motion, personality is conveyed by state *text + the static Core*, never lost.

## 11.10 Design-Language Signature (why a screenshot is unmistakably KRIA)

The recognizability contract — the motifs that must be present so KRIA is never mistaken for generic SaaS:
1. **The Core aura** — a single luminous presence, always upper-left, breathing. KRIA's face.
2. **Ink room + single light** — deep dimensional canvas with one soft radial light source; never flat, never busy.
3. **Aura-glass, floating-only** — translucency/blur exclusively on floating layers (palette/inspector/approvals); content is calm and opaque.
4. **Scarce teal accent** — one hue, used only for intelligence/attention/primary; its rarity is the signature.
5. **Type-led hierarchy** — generous space + a real type scale do the work; few borders, few dividers.
6. **The three-lane Converse** — Conversation / Work / Context — KRIA's unmistakable "think-with-me" layout.
7. **Work blocks** — KRIA's visible thinking rendered as a calm vertical stream of typed blocks.
8. **The risk ramp, reserved** — green→black used only for consequence; when you see it, it always means "a decision."
9. **Lens transitions** — the deliberate "pull into depth" when entering a graph/constellation lens.
10. **Honest empty states + calm micro-motion** — never marketing hero, never decorative animation.
11. **Status line + one presence** — one calm line of "what KRIA is doing," not a cluster of chips.

If a proposed screen lacks these signatures or violates the Universal Design Laws (§24), it is off-brand and must be revised.

The single accent appears on exactly one element: the Send button (idle), the Stop (working), or one inline CTA — never more.

### 11.11.3 State-by-state visual specification
- **Cold empty (first ever):** Core forward and slightly larger; a single quiet line ("What can I help with?"); ≤3 example intent chips (ask / automate / remember). No panels, no rails, no work lane. Maximum calm.
- **Warm empty (returning, new thread):** Core at rest; composer focused; optional 2–3 continue-suggestions (adaptive, dismissible) below the composer. Threads sidebar shows history.
- **Composing:** composer grows; no layout jitter; placeholder rotates gentle examples; nothing else moves.
- **Thinking:** Core → thinking; a slim "KRIA is thinking…" appears at the top of a newly-revealed Work lane; the answer area shows a calm awaiting-cadence (not bouncing dots as the focal element).
- **Planning:** Work lane shows the plan-compare block (paths + chosen); the Conversation lane still leads.
- **Streaming answer:** text streams into the Conversation lane at a composed cadence; tool/result cards attach *within* the reply as L2 (subordinate to the text); Work lane shows the underlying steps; **Stop** is the single accent.
- **Tool/execution:** each active step = one Work block (L2) with status + evidence + its own stop; at most one running-pulse visible; the answer text remains dominant.
- **Approval interruption:** the Conversation lane does **not** spawn an inline modal; instead the Core stills + "glances" toward Approvals, the room desaturates slightly, and the Approval Center presents the decision. Approving/denying returns focus exactly where it was.
- **Error / recovery:** the failing Work block shows a plain-language failure (risk-semantic, icon+text) + inline recovery options (retry/alternative/explain); the conversation is never left in a mystery state; the Core shows recovering.
- **Offline / degraded model:** a quiet degraded chip in the Context rail + Core "limited"; the composer still accepts input (queued); no blank, no blocking.

### 11.11.4 Conversation scrolling philosophy
- **Anchored-to-latest by default:** new content keeps the latest turn in view; during streaming the view follows the stream unless the user scrolls up.
- **Scroll-up freezes follow:** if the user scrolls up to read history, auto-follow pauses and a subtle "jump to latest" affordance appears; returning to bottom resumes follow.
- **Virtualized** (mandatory, §11.6): only visible turns render; scroll position and draft restore on thread switch.
- **Older turns recede:** turns far above gently lower in contrast so the current thought dominates (L1) — a cheap opacity treatment, reduced-motion-safe.

### 11.11.5 Composer specification
- **Position:** sticky bottom of the Conversation lane; a clear gap always separates it from the last message.
- **Growth:** grows with input to a max (~40% of lane height) then scrolls internally.
- **Anatomy (left→right):** attach affordance · input field (primary) · mode chip (Assistant / Lab / tool-lock) · voice entry · **Send** (single accent) which becomes a prominent **Stop** while KRIA works.
- **Behavior:** Enter sends, Shift+Enter newline; draft persists per thread; paste of file/image understood; selection of KRIA's text offers explain/remember/turn-into-automation; slash needs route to the Command Palette (no separate menu).

### 11.11.6 Large-thread handling
- Virtualization + lazy history load (older turns fetched as the user scrolls up).
- A thread that grows very long offers a calm "summarize this thread" affordance (KRIA-authored, provenance-marked) and search-within-thread via the palette.
- Wide content (big tables, code, generated media) is contained within its card with internal scroll; a "focus this result" action opens it in the Inspector or a detached window (never breaks the lane).

### 11.11.7 Focus transitions
- Switching threads/Spaces preserves scroll, selection, and draft; the transition is a fast (~150 ms) calm cross-fade, not a slide that disorients.
- Opening the Work lane or Context rail slides them in without shifting the Conversation lane's reading position.

### 11.11.8 Per-window-mode composition (Converse)
- **Compact (~¼ screen):** Conversation + composer only; Work lane → a one-line "KRIA is working… (expand)" spine that opens as an overlay; Context rail hidden (Inspector-as-overlay); Threads via palette/recent. If an approval is pending it surfaces as a compact-but-complete card. **Curated, not compressed.**
- **Standard:** full three-lane model above (default).
- **Immersive:** Conversation centered with maximal breathing room; Work lane docks fuller on the right; Dock auto-hides (palette leads); rails on demand; approvals + global Stop still surface. Best for long conversations/research.

### 11.11.9 Multi-monitor (Converse)
- A **thread can detach** into its own window (keep chatting while working elsewhere); the detached window carries a subtle Core anchor + its own composer.
- If autonomy is running, the **Approval Center** can live on a second monitor; a pending approval still mirrors to the active window + badges the tray so it is never missed.
- The primary Converse window remains the OS; detached threads are secondary.

### 11.11.10 Acceptance (Converse-specific, adds to DoD §9)
Converse is done when: the eye-path/weights (§11.11.1–2) hold; every state (§11.11.3) is implemented with the specified visual treatment; scrolling behavior (§11.11.4) is correct and virtualized; the composer (§11.11.5) meets its anatomy/behavior; large-thread handling (§11.11.6) works; all three window modes (§11.11.8) compose per spec; approvals never render as inline modals; conversation-dominance holds under every state; reduced-motion keeps it fully usable; performance targets (first-token <50 ms, 60 fps scroll) pass on the Linux matrix.
