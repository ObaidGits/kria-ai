# KRIA GUI Cognition Audit

A brutally honest, evidence-driven architectural audit grounded in the codebase, the failure logs, and the runtime contracts as they exist today.

## Executive Summary

KRIA is **not** a production-grade GUI cognition system. It is a **structural workflow executor** wrapped in the language of cognition. Almost every "GUI cognition" capability you have written either degrades into structural execution or fails verification because the system has no causal model of GUI state. The user-visible failures in the logs are not bugs — they are the architecture telling the truth.

The failures cluster around four hard architectural mistakes:

1. **Two disagreeing sources of completion truth** running in series (HTN structural success + a re-derived `ObservableCompletionEngine` invoked *after* the executor returns), with no causal link between them.
2. **No foreground/focus ownership primitive in the verification path.** The verifier asks "is the focused window's title 'code'?" right after launching VS Code — at which point focus has returned to KRIA itself.
3. **Category errors in `ExecutionTarget`.** The same enum carries "where do commands run" (host/vm/docker) and "what tool category" (browser/mcp/cloud_provider). This is the source of the `managed_browser_navigate cannot execute on 'browser'` failure.
4. **An overgrown agent layer** — 117 files, ~50k lines in `agent/`, an 8,200-line `loop_engine/mod.rs`, three verifier flavours, a planner, a `planner_v2`, a `gui_planner`, a `gui_substrate_planner`, an HTN executor, two intent compilers, an opgraph compiler, a workflow compiler, plus modules named `ambient_cognition`, `curiosity`, `self_model`, `psdg`, `world_model`, `executive` etc. The cognition layer has accumulated faster than the runtime contracts under it stabilised.

Until those four are fixed, no amount of new "cognition" will move the needle. Adding more retries, more probes, more semantic layers will make the failure mode harder to see, not easier.

## What KRIA Currently Actually Is

Looking at what the code does, not what it calls itself:

- **The substrate planner (`gui_substrate_planner.rs`, 3034 lines)** is the only thing that works reliably in the logs. It picks `IdeCodeRunWorkflow` / `FileWriteThenOpen` / `TerminalExecution` / `BrowserNavigate`, all of which avoid GUI input as much as possible. They do `write_file` + `open_application_with_file` + bash redirection to capture output. None of this is cognition. It is **deterministic substrate routing of declarative goals to filesystem and process primitives**, dressed up as workflow semantics.
- **The HTN executor** runs that 4-step plan with `FileSystemEffect` / `ProcessLaunched` / `DeterministicOutput` verifications. These are not GUI verifications — they are filesystem and `/proc` checks. They succeed.
- **At that point KRIA's structural truth says "Task completed."** This is what the first run in the log shows: *"Task completed. KRIA verified 1 step in 1888ms."*
- **Then `ObservableCompletionEngine` runs again on the same prompt** (loop_engine/mod.rs ~4720), re-derives outcomes from the user text via `infer_outcomes`, builds policies via `CompletionVisibilityPolicy::for_outcome`, fans them through `BoundedExecutionVerifier`, and asserts: "is the focused window's title containing 'code'?". It can't be true — KRIA's chat is focused. So the narrative it appends is `⚠ Expected outcome not yet visible`.
- The user sees a contradiction in a single response: "Task completed" + "outcome not yet visible". Then in later runs, `format_gui_workflow_partial_for_user` flips the framing entirely to "Task partially completed" because of `observable_narrative_requires_partial_completion`. The system is arguing with itself.

So functionally KRIA today is:

> **A deterministic substrate-routing executor with an out-of-band screenshot-style verifier that tries (and fails) to retrofit GUI cognition onto a workflow that was already complete.**

Not a GUI agent. Not a workflow executor in the strict sense. Not a cognition system. It is a hybrid that contradicts itself.

## Root Architectural Failure Analysis

### Why GUI Cognition Is Failing

There is no model of what is actually happening on the screen. The "cognition" lives in three disconnected places:

- the substrate planner's **declarative intent → workflow** translation,
- the bounded verifier's **point-in-time accessibility queries**,
- the observable completion engine's **post-hoc text-derived re-verification**.

None of them share state. None of them know what the others did. The verifier never sees the workflow it's verifying — it gets a `Verifiability` leaf that was either generated by the planner or re-derived from the user prompt. The visibility check has no PID, no window handle, no causal link to the launch. So when `verify_xdotool_window(title_contains: Some("code"))` runs, it asks "does the *currently focused* window have 'code' in its title?" — and after the IDE was launched and KRIA's chat window stole focus back, the answer is permanently no.

Cognition cannot exist without a state model. There is no state model.

### Why Workflow Semantics Collapse

Workflow semantics collapse at the **boundary between a structural success and a visible success**. Look at:

```rust
// loop_engine/mod.rs ~4720
if result.success {
    let visible_contract_incomplete = observable_narrative_requires_partial_completion(...);
    let summary = if visible_contract_incomplete {
        format_gui_workflow_partial_for_user(...)
    } else {
        format_gui_workflow_success_for_user(...)
    };
}
```

`result.success` was set inside `htn_executor` (`htn_executor.rs:2369`) the moment the last step's *structural* verification passed. The visibility narrative is then attached on top, and the surface message is *negotiated* between two systems that both claim authority. There is no single source of truth. There is no single contract. Workflow semantics collapse into framing decisions.

### Why Visible Workflows Degrade Into Backend Execution

Because the substrate planner deliberately avoids GUI input. This is correct on Wayland — `xdotool` doesn't work, AT-SPI is partial, GUI input is unreliable — but the architecture treats this as a feature ("execution intelligence") while the verifier still expects visible-workflow truth. The planner says "I'll write a file and open it with the editor; that's the same goal." The verifier says "I expect the focused window's title to contain 'code' for 2.5 seconds." Those two contracts disagree.

The honest position is one of:

- a) "structural execution is the contract" — drop the screen-focus verifier,
- b) "visible execution is the contract" — drop the substrate shortcut,
- c) "both, with explicit modes" — but right now neither is declared and neither is enforced.

KRIA today silently does (a) and pretends to do (b).

### Wayland / X11 / XWayland Reality

You have correct intuitions in the code (the substrate-planner module comment cites Wayland incompatibility as the reason for `FileWriteThenOpen`), but the verifier never internalised them. Concretely:

- `verify_xdotool_window` is X11-only. The error message `xdotool active window: 'K.R.I.A.' class=''` proves it ran inside an XWayland-backed KRIA window — class is empty because xdotool doesn't see the WM_CLASS through the compositor reliably.
- `verify_atspi_window` requires `gsettings ... toolkit-accessibility true`, the AT-SPI bus, and the target app actually exposing an accessibility tree. Many Electron and Chromium apps don't unless launched with `--force-renderer-accessibility`. The check at `atspi_engine.rs:detect_capabilities` exists, but **its result does not gate the verification path**. The verifier just runs and returns "no match" or "Unobservable" rather than declaring "verification not possible in this environment".
- The Wayland fallback in `kria-uinput-daemon` (`/proc` heuristic for "most recently started GUI process") is a reasonable last resort for active-window detection, **but the verifier doesn't use it**.
- There is no compositor-aware capability. The decision to run a visible verification should be conditioned on (session_type, compositor, AT-SPI live, target-app accessibility) at minimum. It isn't.

The blunt truth: **on Wayland, KRIA cannot reliably verify a "visible workflow" without compositor cooperation that doesn't exist on GNOME/KDE for arbitrary apps.** Pretending otherwise will keep producing false partials.

### Verifier Architecture Audit

You have **three** verifier paths still alive:

- `BoundedExecutionVerifier` (1140 lines) — the "production" one.
- `execution_verifier_impl.rs` (1401 lines) — described in `BoundedExecutionVerifier`'s docs as "replaced", but still in the tree.
- A scattering of `verify_*` helpers and the `ObservableCompletionEngine` that wraps `BoundedExecutionVerifier` with its own timeout (`policy.verify_timeout_ms`, often 1500-2500ms) inside the verifier's own 2000ms `MAX_VERIFY_MS` cap. The two timeouts can interact unintuitively: if the policy timeout (2500ms) exceeds the verifier's MAX (2000ms), the policy's wait is dead code; if it's shorter (1500ms for `OutputMustBeSurfaced`), it cuts off legitimate window focus settling.

Inside `verify_window_state` you have a 200ms initial delay and 5×200ms polling (1200ms minimum). That's longer than `policy.verify_timeout_ms = 1500` for surfacing checks. The verifier will time out before it has finished its own polling budget. This is exactly what the log shows: `Verification timed out after 2000ms` — the OCE's 2.5s policy timed out against the verifier's 2.0s hard cap **after** the verifier was already mid-polling.

The verifier also conflates "outcome wasn't observed" with "verification couldn't run". `Unobservable` is returned both when AT-SPI is gone *and* when the AT-SPI tree just doesn't yet contain the freshly launched app. From the caller's perspective these are indistinguishable — and both are reported as "outcome not yet visible", which is incorrect for the first case.

### Planner / Substrate / Executor Audit

You have at least these planning surfaces:

- `intent_compiler.rs` / `intent_compiler_rule.rs` / `intent_compiler_llm.rs` — text → `GuiTaskSpec`.
- `gui_substrate_planner.rs` — `GuiTaskSpec` → `GuiWorkflow` (the deterministic, working layer).
- `gui_planner.rs`, `planner.rs`, `planner_v2/mod.rs` — older / parallel planners.
- `workflow_compiler.rs`, `semantic_workflow.rs`, `workflow_intent_contract.rs`, `workflow_session.rs` — semantic workflow layer.
- `htn_executor.rs` (4059 lines) — final execution.
- `opgraph.rs`, `opgraph_compiler.rs` — yet another execution graph.
- `stage_executor.rs`, `resume_executor.rs`, `htn_integration.rs`, `hybrid_synchronization.rs` — orchestration.

This is a planner ecosystem, not a planner. For the same prompt, it's not deterministic which planner runs first, which fallback fires, and what verification leaf gets generated. This is overengineering directly. **Production GUI cognition needs one planner with one verification contract, not five planners with five contracts.**

The substrate planner is the only one that demonstrably works. Everything else either gates it (intent compiler) or runs after it (HTN executor). The other planners look like staging grounds for ideas that didn't displace the substrate planner. They are debt.

### Semantic Intent → Runtime Action Audit

The substrate planner is right: declarative goals like "write a fibonacci program in gedit" should not become character-by-character keystrokes. But the intent compiler produces `Verb::Open + Target::App + Content::Generated` and that exact triple doesn't survive translation:

- `(Verb::Open, App=code, Generated{language=python})` → `IdeCodeRunWorkflow` if `is_ide_app(app)`, else `TerminalExecution`. This decision lives inside `gui_substrate_planner.rs` rather than in the intent layer. It's a runtime branch with no recorded contract.
- `(Verb::Open, App="Excel or Calc", _)` is sent to `app_lifecycle.rs` which calls `registry.resolve_alias("Excel or Calc")` and gets `None`, returning `application 'Excel or Calc' is not found in the installed app registry`. The intent compiler did not split the disjunctive alias, the substrate planner did not normalize it, and the registry rejected it because it's a strict alphanumeric alias map. **The "or" is a semantic operator the system does not recognise.** This is a planner-layer bug masquerading as a registry error.

Semantic intent collapse points:

1. Disjunctive app names (`A or B`) — no resolver.
2. Browser tool categories vs. browser execution targets — `ExecutionTarget::Browser` is both a tool's "where to run" and a tool category. The fact that `managed_browser_navigate` resolves to `target=Browser` and was rejected with `Allowed targets: [host]` (in your build) is the bug surfacing.
3. "Open a browser and go to URL" — should produce `BrowserNavigate` substrate. It does. But the execution authority then validates the `managed_browser_navigate` tool against an `ExecutionTarget::Browser` binding which the policy table recently lacked. Even after the fix to `browser_or_host()`, this whole layer is enforcing target rules on a tool whose physical target is *the host process* (the launched browser), not "browser" in any architectural sense.

### Capability Model Audit

The capability model is shallow. `AccessibilityCapabilities` exists in `atspi_engine.rs` but is not part of the planning decision. The planner does not branch on:

- session type (X11 / Wayland / XWayland),
- AT-SPI operationality,
- target app's accessibility tree availability,
- compositor identity (mutter, kwin, sway),
- whether the foreground lease is currently held by the user,
- whether the user has another window in front and would object to focus theft.

The planner emits the same plan for any environment. The verifier emits the same probe for any environment. **A capability-driven planner would refuse to declare a `WindowState` verification leaf when the environment cannot satisfy it**, and would fall back to `FileSystemEffect`/`ProcessLaunched` only — closing the gap between contracted truth and observable truth.

### GUI Visibility Verification Audit

Two structural problems beyond what's already covered:

1. **No causal binding from launch to verification.** `open_application_with_file` returns success when the launcher (gio-launch / xdg-open / desktop entry) has accepted the request. It does not return the launched PID or window ID. The verifier searches the focused window globally for substring "code". Even when it works, it's verifying "*some* window is focused with 'code' in the title" — not "the window we launched is visible". Drop a Code-named editor running in the background and you get a false positive.
2. **Title substring "code" is dangerously generic.** A window named "VS Code - foo.py" matches; "Tap to type passcode" also matches; "QR code reader" also matches. The check carries no notion of *which* code.

### Environment Grounding Audit

`environment_grounder.rs` is 1768 lines. Whatever it grounds, it does not feed into the visibility verifier. The verifier's grounding consists of: "run xdotool, run AT-SPI, run OCR." That isn't grounding — that is repeated probing. Grounding should establish a **stable, point-in-time snapshot** with a freshness budget and a known confidence, used by *all* verification leaves for that workflow. There is none.

### Workflow Fidelity Audit

Workflow fidelity is broken at the boundary between sub-goal verification and outcome verification.

- Sub-goal verification (`htn_executor`) verifies what each step physically did. This is solid for filesystem / process / output.
- Outcome verification (`ObservableCompletionEngine`) verifies what the user said they wanted. This is broken because it re-derives outcomes from the user text ignoring what the planner actually decided, and it has no causal handle on what the executor produced.

Concrete: when the substrate planner picks `IdeCodeRunWorkflow`, the *workflow itself* knows the IDE's expected window-title hint, the file PID, and the captured-output file. The OCE *throws all of that away* and re-derives `ObservableOutcome::ApplicationWindow { app_name: "code", title_hint: None }` from the user's text. The workflow has the truth and the verifier won't read it.

That single bug — re-derivation instead of plan-derivation — is the largest source of false partials in the logs.

### HITL / Approval / Visibility Audit

There is a comprehensive HITL system (`collaborative_decision.rs`, 2585 lines) but it is invoked for **target ambiguity and policy approval**, not for **visibility uncertainty**. When the verifier returns `Unobservable`, no HITL prompt is raised: the system just narrates a partial. Production cognition would prefer "I think it worked but I can't see it — should I bring the window forward to confirm?". Today there is no such path.

### Frontend ↔ Backend Contract Audit

The contract shipped to the frontend is the surface message. It changes shape across runs:

- Run A: `Task completed. … ⚠ Expected outcome not yet visible: …`
- Run B: `Task partially completed. KRIA verified 1 step structurally … but the required visible outcome was not verified.`
- Run C: `⚠️ Task did not fully complete. KRIA verified 0 of 1 step before stopping. Failure: …`

The shape of the response (`StreamEvent::Token` + `StreamEvent::Done` vs `StreamEvent::Error` + `StreamEvent::Done`) implicitly carries the contract, with no structured field that says "this was a structural success but a visible failure", "this was a target rejection", "this was an LLM failure". The frontend cannot adapt because there is no machine-readable signal — only a shifting natural-language prefix.

### Runtime Ownership And Synchronization Audit

There is a `ForegroundLeaseManager` (`gui_lease.rs`) but it is not held during outcome verification. The substrate planner doesn't acquire a foreground lease for `open_application_with_file`. The HTN executor doesn't either. The verifier runs *after* the executor returns control, by which time:

- focus has bounced back to KRIA,
- compositor animations may still be playing,
- the launched app may not yet have an accessibility tree.

Synchronization is implicit (`tokio::time::sleep`) rather than reactive (wait for `Window::Mapped`/`AT-SPI::ChildAdded`/etc.). There is no event-driven completion. A production GUI agent must be event-driven, with explicit ownership: lease the foreground, observe the appearance event, release the lease.

### Focus / Window / Active Surface Truth Audit

This is the single most damaging design flaw. The verifier asks "what is *currently* focused?" right after the executor finishes. That is the wrong question. The right questions are:

- "Did the launched process attach a window?"
- "Is that window mapped (visible)?"
- "Is the foreground lease still owned by us so the user can see it?"

None of those are asked. So focus truth is a coin flip that lands tails because KRIA's own UI has refocused.

## Why Existing Plans Did Not Solve The Problem

You have iterated correctly on **subsystems** while the **contracts between them** stayed broken. Specifically:

- The substrate planner solves "how to actually do the task." It works.
- The bounded verifier solves "how to probe a class of evidence." It mostly works in isolation.
- The observable completion engine solves "what did the user expect." It also works in isolation.

But the **contract between executor and verifier is missing**. The OCE re-runs intent inference, doesn't see the executor's plan, and asks the verifier the wrong questions. Adding more variants of any of those three modules does not fix that contract.

Past plans did not solve the problem because they treated it as a quality issue (more probes, more retries, more semantic layers) rather than a contract issue (one workflow, one expected outcome list, one verification contract, one source of truth, one user-visible decision). That is why this audit lands on simplification, not addition.

## Which Existing Architectural Ideas Are Correct

Keep these. They are good.

- **Substrate routing (`gui_substrate_planner.rs`).** Picking `FileWriteThenOpen` instead of keystroke injection on Wayland is the correct call. This is the engineering insight that should be **doubled down on**, not diluted.
- **`Verifiability` leaves.** A small enum of verifiable evidence classes is the right primitive. Keep it. Restrict it.
- **Execution authority for VM/Host destructive shell commands.** The "you said 'rm -rf'; on host or VM?" path is genuinely useful. Keep it for shell tools.
- **Foreground lease primitive.** The idea is right. It just isn't used where it matters.
- **AT-SPI capability detection.** The `accessibility_doctor()` exists; use its output to gate decisions.
- **HITL infrastructure.** Solid. Wire it into visibility uncertainty too.
- **`Operation` taxonomy in `turn_gate`.** Good shape; useful for visibility policy derivation.

## Which Architectural Ideas Are Fundamentally Wrong

Drop these or quarantine them.

- **`ExecutionTarget::Browser`, `ExecutionTarget::Mcp`, `ExecutionTarget::CloudProvider` as siblings of `Host/Vm/Docker`.** This is a category error. `ExecutionTarget` should be **only** `Host | Vm | Docker | Colab` — environments where shell-equivalent commands run. "Browser" is a *tool category*, not an execution target. Authorization for browser tools should not flow through `ExecutionTarget`. Fix this and the `EXECUTION_BLOCKED: cannot execute on 'browser'` class of bugs becomes structurally impossible.
- **OCE re-deriving outcomes from user text instead of the executed plan.** Wrong source. The plan owns the outcome contract.
- **Multiple parallel planners (`planner.rs`, `planner_v2`, `gui_planner`, `gui_substrate_planner`, `workflow_compiler`, `semantic_workflow`, `opgraph_compiler`).** Pick one. Substrate planner. Delete the rest.
- **Two timeouts stacked (OCE policy timeout vs verifier MAX).** Pick one.
- **`execution_verifier_impl.rs` co-existing with `BoundedExecutionVerifier`.** Pick one.
- **`Verb::Other(String)` smuggling raw text through the planner.** This is a typing escape hatch that defeats the type system. Either parse it or reject it; do not pass strings through enums.
- **`describe_outcome_short` writing user-facing English from inside a verifier**. UX strings inside cognition modules are debt.
- **`ambient_cognition`, `curiosity`, `self_model`, `psdg`/`world_model` running before the basic GUI verification contract is right.** These are cognition-flavoured modules built on top of an unstable runtime. They will encode and amplify the contract drift, not fix it.

## Overengineering Analysis

The agent layer carries the unmistakable signature of accreted experiments:

- `agent/` has 117 files and ~50k lines.
- `loop_engine/mod.rs` is 8,200 lines. It is impossible to reason about as a single unit.
- `htn_executor.rs` is 4,059 lines. It includes inline 105-step cap tests, window-switch tests, halt-engaged tests, etc. — production code interleaved with integration tests in the same file.
- `gui_substrate_planner.rs` is 3,034 lines containing both planner logic and 200+ lines of test fixtures.
- Three intent compilers (`intent_compiler.rs`, `intent_compiler_rule.rs`, `intent_compiler_llm.rs`).
- Two execution gates (`execution_gate.rs`, `intent_gate.rs`, `turn_gate.rs`).
- Multiple workflow modules with overlapping vocabulary (`workflow_session`, `workflow_continuation`, `workflow_compiler`, `workflow_expectation`, `workflow_intent_contract`, `semantic_workflow`).

The cost: every change has to traverse five intermediate layers, each of which can independently be wrong, and the LLM-or-human reading the code cannot predict where a behaviour comes from.

## Missing Production-Grade Primitives

These are the primitives KRIA does **not** have and a production GUI agent **must**:

1. **Workflow-bound outcome contract.** `WorkflowResult` should carry the *exact set of expected outcomes*, generated by the planner, not re-derived by the verifier.
2. **Causal launch handle.** `open_application_with_file` should return `(pid, launch_id, expected_window_class)` so the verifier can match by causal identity, not substring.
3. **Window mapped / appeared event.** A single async primitive `WindowObserver::wait_for_window(class_or_pid, deadline)` that completes on compositor "Map" event (or AT-SPI ChildAdded), with a fallback poll loop. Today, polling is the only path.
4. **Foreground lease guard during verification.** While verifying visibility, KRIA must hold a lease that suppresses its own focus-stealing.
5. **Verification capability declaration per environment.** Compose `(session_type, atspi_state, target_app_capability) → CapabilitySet`, used to *prune* `Verifiability` leaves before they are emitted. If a leaf cannot be satisfied here, the planner downgrades the contract to what *can* be observed, and reports that honestly.
6. **One ExecutionEnvironment enum** (`Host | Vm | Docker | Colab`) plus an orthogonal `ToolCategory` (`shell | filesystem | browser | mcp | google_workspace | image | …`). The validators must take `(category, environment)` separately.
7. **Single failure taxonomy** with explicit kinds: `StructuralFailure`, `VisibleFailure`, `Unobservable`, `EnvironmentNotCapable`, `TargetMismatch`, `ModelUnavailable`, `Aborted`. Today these are partially encoded in error strings.
8. **One workflow finalizer.** The decision "complete | partial | failed | unverifiable" must be emitted **once**, by **one place**, with the *full* contract in scope.
9. **Plan-time HITL escalation for unverifiable outcomes.** When the planner knows the environment can't observe an outcome, ask the user up-front whether to proceed structurally — don't promise visible verification you can't deliver.
10. **First-class semantic alias resolver in the intent compiler.** `Excel or Calc` becomes `[App("excel"), App("libreoffice-calc")]`, planner picks the first installed one. Today, the resolution layer doesn't exist between text and the registry.

## Missing Deterministic Runtime Contracts

- **`ExecutionEnvironment` purity** (above).
- **`OutcomeContract`**: a typed list of `ObservableOutcome` attached to the `GuiWorkflow` at plan time, threaded through the executor, consumed by the verifier. No re-derivation.
- **`VerifierTimeoutBudget`**: a single budget per verification, not stacked.
- **`CompletionVerdict`**: `{ Complete | Partial(reason) | Unverifiable(reason) | Failed(reason) }`. Frontend keys off this, not off natural language.

## Hidden Contradictions In The Architecture

- "Substrate planner avoids GUI input because Wayland is unreliable" + "OCE expects visible focus verification on Wayland." Pick one.
- "Execution authority distinguishes targets by safety boundary" + "Browser is also a target." Browser is not a safety boundary; the host process is.
- "OCE infers outcomes from user text" + "Substrate planner already decided what to do." Two sources of truth.
- "Verifier timeout is hard-capped at 2000ms inside `BoundedExecutionVerifier`" + "Policy timeouts of 2500ms exist." The longer one is dead code today.
- "Target = `Browser`, allowed targets `[Host]`" message in production logs vs `browser_or_host` policy in current code. Either the binary in the user's session was older or there's a second policy path I missed; in either case, the fact that this message is **possible** means the type system isn't preventing it. It should.

## False Success / Partial Success Semantics Audit

- **Run 1** ("Open Code, create a Python file, run it"): structural truth = success (file written, process running, output captured); visible truth = unknown (probe timed out at 750ms which is shorter than `INITIAL_FOCUS_DELAY_MS=200` + first poll at 200ms = 400ms, but the AT-SPI engine probe latency dominates). Surface message: "Task completed" + "outcome not yet visible". **Contradictory**.
- **Run 4** (Excel or Calc): structural truth = failure (alias unknown); surface message: "application 'Excel or Calc' is not found" — accurate but **the whole substrate planner never got a chance to translate the disjunction**.
- **Run 5** (Draft email): structural truth = LLM dispatch failed; surface message: "AI model is currently unavailable. For GUI automation tasks…". This is an LLM-error path leaking into GUI advice — meaning the substrate planner did **not** trigger for this prompt, the system fell to ReAct, and the ReAct branch had to call the LLM and got nothing. So the substrate planner's coverage is narrower than the user-visible GUI surface advertises.

## Why The Current System Still Feels Like A Prototype

Three concrete reasons:

1. **The most important contracts are implicit.** "Done" means different things in different code paths. Until "Done" has one definition, every other quality investment is fighting drift.
2. **Cognition modules are stacked on top of unstable runtime contracts.** PSDG, world_model, ambient_cognition, curiosity all encode beliefs about state that cannot be made true by the underlying runtime today.
3. **Single-file giants** (`loop_engine/mod.rs` at 8200 lines) make the runtime opaque even to the people maintaining it.

## What A Production-Grade GUI Cognition System Actually Requires

In order of indispensability:

1. **A canonical, plan-bound outcome contract.** Plan declares outcomes; executor enforces; verifier observes; finalizer judges. Once.
2. **Capability-driven verification contracts.** The plan's outcome set is *projected* through the current environment capability into a verifiable subset. What can't be verified is declared up-front, not pretended after.
3. **Causal launch handles + event-driven appearance detection.** No substring focus polling.
4. **Foreground lease ownership during verification.**
5. **Pure execution-environment enum** (Host/Vm/Docker/Colab), separate from tool category.
6. **Deterministic substrate planner** (which you have) extended to cover the long tail (alias disjunctions, terminal-with-command, drafts).
7. **One verifier with one timeout budget.**
8. **One finalizer with one structured verdict.**
9. **Sober refusal.** When the system cannot reasonably do or verify a task in this environment, say so. Better than silently degrading.

## Recommended Final Architectural Direction

**Direction: collapse the cognition layer into a thin runtime spine, treat substrate execution as the default, treat visible verification as an opt-in capability.**

### What Should Be Removed

- `planner.rs`, `planner_v2/mod.rs`, `gui_planner.rs`. Keep only `gui_substrate_planner.rs` as the planner.
- `execution_verifier_impl.rs` — folded into `BoundedExecutionVerifier`.
- `workflow_compiler.rs`, `semantic_workflow.rs`, `workflow_intent_contract.rs` — collapse into a single `workflow.rs` of <500 lines defining `Workflow`, `OutcomeContract`, `Verdict`.
- `opgraph.rs`, `opgraph_compiler.rs`. The substrate planner doesn't need opgraphs.
- `ambient_cognition`, `curiosity`, `self_model`, `psdg` for the GUI path. They can re-enter once the runtime is stable. Quarantine them into a feature flag for now.
- `ExecutionTarget::Browser`, `ExecutionTarget::Mcp`, `ExecutionTarget::CloudProvider` (replaced by `ToolCategory`).
- The OCE's `infer_outcomes` re-derivation when a workflow contract exists.

### What Should Be Simplified

- `loop_engine/mod.rs`: split by concern (LLM dispatch, GUI routing, outcome finalisation) into ~4 files of <1500 lines each.
- `htn_executor.rs`: extract its tests; reduce to executor + verification dispatch.
- Verifier timeout: one budget, attached to the leaf, no nested caps.

### What Should Be Rewritten

- The OCE → `OutcomeContract` derivation. Plan-time, not post-hoc.
- The execution-authority `ExecutionTarget` enum and policy table.
- The visibility verification path: replace global focus polling with PID/window-class-bound observation backed by an event source.

### What Should Stay Structural Instead Of GUI

For the foreseeable future, on Wayland, **make structural execution the contract for**:

- "open editor + write code + run + show output" (already true via `IdeCodeRunWorkflow`),
- "open browser + go to URL" (verify via CDP only, never via window focus),
- "open file manager and show home" (verify via process running + path argument),
- "open spreadsheet and create columns" (verify via filesystem .csv/.xlsx written),
- "draft email" (verify via file/draft saved, optionally surface via deep link).

Visibility is then a **bonus**, not a contract.

### What Should Become Capability-Driven

- Whether a `Verifiability::WindowState` leaf is even legal to emit.
- Whether interaction-heavy substrates (`InteractionHeavy`, `Keystroke`) are even attempted.
- Whether AT-SPI / xdotool / OCR fallbacks are tried in this environment.

### What Should Remain Deterministic (Never LLM-Driven)

- Substrate selection (`FileWriteThenOpen` vs `IdeCodeRunWorkflow` etc.).
- Verification leaf generation.
- Execution authority (target validation).
- Completion verdict.
- Resource lease arbitration.
- Failure taxonomy classification.

### What Should NEVER Become LLM-Driven

- Anything that decides whether a task succeeded.
- Anything that decides whether to escalate to HITL.
- Anything that decides whether to cross a destructive threshold.
- Anything that decides whether to emit a UI claim of completion.

The LLM is excellent at intent extraction and content generation. It is unfit for adjudicating completion truth.

### Minimal Survivable Production Architecture

```text
turn_gate ── intent_compiler ── substrate_planner ── workflow{contract,steps}
                                                          │
                                            ┌── htn_executor ──┐
                                            │                  │
                                       per-step verifier   plan_outcome_verifier
                                            └────── ▼ ────────┘
                                              workflow_finalizer
                                              ↓ Verdict
                                              ↓ user message
```

Five real components, each with one job, each <2000 lines. Everything else is supporting infrastructure or out of scope for this contract.

### Recommended Implementation Order

1. **Split `ExecutionTarget`** into `ExecutionEnvironment` (Host/Vm/Docker/Colab) + `ToolCategory`. Update execution authority. Tests will catch any drift.
2. **Bind `OutcomeContract` to `GuiWorkflow`.** Make the planner emit it. Make the executor pass it through. Make the OCE consume it instead of re-deriving from text.
3. **One verifier, one timeout budget.** Delete `execution_verifier_impl.rs`.
4. **Capability-aware planner.** Detect environment once at session start; cache; gate `Verifiability` leaves.
5. **Single completion verdict.** Replace the dual narrative path with a structured `Verdict` enum surfaced through one formatter.
6. **Disjunctive alias resolver.** Tiny change in intent compiler. Big UX win.
7. **Causal launch handles.** Returns PID/window class from `open_application_with_file`. Used by verifier.
8. **Foreground lease wrapping the whole verifier**, with explicit "may steal focus from KRIA chat" semantics.
9. Then, and only then, revisit `psdg` / `world_model` / `ambient_cognition` for re-introduction.

### Highest-ROI Fixes

- (1) Fix `ExecutionTarget` category error — eliminates a class of `EXECUTION_BLOCKED` bugs.
- (2) Plan-bound outcome contract — eliminates "Task completed" + "not yet visible" contradiction.
- (3) Disjunctive alias resolver — eliminates "Excel or Calc not found" class of failures.
- (5) Single verdict — fixes UX contract drift with the frontend.

These four are days of work. The rest is weeks-to-months.

### Highest-Risk Areas

- The 8200-line `loop_engine/mod.rs` is a refactor risk. Break it up incrementally with characterization tests; do not rewrite in one go.
- Wayland visibility verification — accept it cannot be made strong without compositor cooperation. Don't burn cycles trying.
- HITL escalation in the cognition path — adding new prompts mid-workflow is high UX risk; gate behind explicit policies.

### Hard Truths / Non-Negotiable Constraints

- **You cannot make Wayland focus verification reliable for arbitrary apps.** Don't promise it.
- **A focused-window-substring check is never a workflow completion proof.** Stop using it as one.
- **Two parallel sources of completion truth always disagree.** Collapse to one.
- **More cognition modules on top of unstable contracts make systems harder to debug, not easier.** Stabilise first.
- **Substrate execution is the only thing currently working at scale.** Stop apologising for it. Make it the contract.

## Final Verdict

**Can KRIA realistically become a production-grade GUI cognition system with the current architectural direction?**

Not on the current direction. On a *simplified* direction, yes — but only if you accept what the runtime is actually able to do today and stop pretending it does more.

Specifically:

- **Yes** if "GUI cognition" means: deterministic substrate routing of declarative goals into filesystem/process/CDP primitives, with environment-capability-gated visibility verification, plan-bound outcome contracts, one verifier, one verdict, and honest refusal when the environment cannot satisfy a visible-state demand.
- **No** if "GUI cognition" means: keystroke-driven, OCR-verified, focus-stealing, fully visible-workflow agentic execution on arbitrary Wayland desktops with arbitrary apps. That is unreachable with the primitives we currently have access to in user space, and adding more cognition layers will not change that.

The mandatory changes for the realistic path are:

1. Collapse `ExecutionTarget` category error.
2. Make outcome contracts plan-bound, not text-re-derived.
3. One verifier, one timeout, one verdict.
4. Capability-driven verification leaves.
5. Causal launch handles + event-driven appearance + foreground lease during verification.
6. Disjunctive semantic alias resolution at the planner.
7. Quarantine the speculative cognition layers (psdg/world_model/ambient/etc.) until 1-6 ship.
8. Break up the 8000+-line god files by concern.
9. Accept that on Wayland, structural execution is the contract; visibility is an opt-in bonus.

If those nine ship, KRIA will be a small, sharp, honest GUI assistant that is reliable on Linux. If they don't, you will keep building cognition on top of contradicting truths — and the failure mode will keep widening.
